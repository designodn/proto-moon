# Тиражирование прототипирования с агентами на другие БЮ

Материал к выступлению, оформлен таблицами. Сводка — ниже, детали — в разделах 1–4.

**Тезис:** тиражируем **не прототип, а обвязку вокруг него** — правила сборки,
агентов-проверяющих и контур данных. Форма поставки — **плагин Claude Code +
шаблон-репозиторий**, ставится в чужой БЮ за один день.

**Допущения** (поправьте под факт): целевой пользователь — дизайнер, который не пишет
код; DS у БЮ в основном общая, фазу инвентаризации закладываем; цель выступления —
добро и ресурсы на пилот с 1–2 БЮ.

## 1. Образ результата

### 1.1. Что тиражируем — три слоя

| Слой | Что это | Тиражируется как |
|---|---|---|
| **A. Материал** | DS-компоненты (`components/`, ~120 файлов), токены (`tokens.css`), шрифты, иконки | Шаблон-репозиторий или подключаемый пакет DS |
| **B. Метод** | Правила сборки (`CLAUDE.md`), спеки разделов, 4 агента, скилл `fetch-all`, git-хуки | **Плагин Claude Code — главный артефакт** |
| **C. Контент-контур** | Google-таблица как CMS → 11 fetch-скриптов → статический JSON + запечённый HTML + медиа-кэш | Скилл и скрипты внутри плагина, шаблон таблицы отдельно |

### 1.2. Что внутри плагина

| Компонент | Тип | Что делает |
|---|---|---|
| `/proto-init` | команда | Бутстрап: спрашивает БЮ, DS, набор экранов; генерирует `CLAUDE.md` под этот БЮ, подключает деплой, заводит таблицу из шаблона |
| `fetch-all` | скилл | Синхронизация контента из таблицы: 12 листов, инкрементально по хэшу, медиа-кэш с пережатием в webp |
| `macket-rules-checker` | субагент | Линтер по правилам перед коммитом: DS-компоненты вместо самописных, токены вместо хардкода. Вердикт PASS/FAIL с `file:line` |
| `screenshot-testing` | субагент | Гоняет страницу в реальном Chromium: тапы, свайпы, скриншоты, замер computed styles. Проверяет, что интерактив действительно работает |
| `kirill` | субагент | Проводник для новичка: «куда нажать, что сделать, как попросить». Заменяет человека-наставника на онбординге |
| `macket-insights-curator` | субагент по крону | Раз в неделю переносит устойчивые находки из инсайтов в чек-лист линтера и в правила |
| `pre-commit` | хук | Детерминированная типографика на каждом коммите — без участия человека |

### 1.2.1. Развёрнуто: что это технически, как ставится, как работает

*(Текстовая версия раздела 1 — для устного рассказа.)*

**Что такое плагин.** Каталог с манифестом `.claude-plugin/plugin.json`, который
кладёт в чужой проект сразу весь набор: скиллы, субагентов, слэш-команды, хуки и
настройки. Не документ, не архив, не инструкция — устанавливаемая единица с версией.

```
proto-kit/
├── .claude-plugin/plugin.json     # манифест: имя, версия, описание
├── commands/proto-init.md         # слэш-команда бутстрапа
├── agents/                        # 4 субагента
│   ├── macket-rules-checker.md    #   линтер правил перед коммитом
│   ├── screenshot-testing.md      #   прогон в реальном Chromium
│   ├── kirill.md                  #   проводник для новичка
│   └── insights-curator.md        #   куратор правил, по крону
├── skills/fetch-content/          # скилл синхронизации контента
├── scripts/                       # fetch-скрипты, nbsp, деплой
├── hooks/hooks.json               # pre-commit, SessionStart
└── templates/                     # заготовка CLAUDE.md, шаблон таблицы
```

Второй артефакт — **template-репозиторий**: пустой стартер с DS, токенами,
настроенным деплоем и `index.html`. Нужен тем БЮ, у кого нет своего фронтенд-проекта,
— иначе плагин ставить некуда. Разделение принципиальное: плагин это метод, он общий
и обновляется централизованно; репозиторий это контент БЮ, он их собственный.

**Установка — две команды.**

```
/plugin marketplace add <внутренний-репозиторий-маркетплейса>
/plugin install proto-kit@ok-design
```

Первая подключает внутренний каталог плагинов (обычный git-репозиторий с манифестом
маркетплейса). Вторая ставит плагин: в проекте появляются все агенты, скилл и
команда. Обновление — переустановка той же командой.

**Настройка — `/proto-init`.** Команда-диалог, а не конфиг для ручного
редактирования. Спрашивает: какое БЮ и продукт; где лежит дизайн-система — общая DS
ОК или своя, и в каком виде доступны компоненты и токены; какие экраны нужны на
старте; откуда берётся контент; куда деплоить. На выходе генерирует `CLAUDE.md` под
этот БЮ, подключает нужные скрипты, заводит таблицу-контент из шаблона и настраивает
автодеплой.

Пункт важный: у нас `CLAUDE.md` писался месяц по мере набивания шишек. Дизайнер
чужого БЮ не должен проходить этот путь заново — бутстрап отдаёт готовый результат.

**Сборка экрана.** Дизайнер пишет обычной фразой: «собери экран ленты с карточками
событий, табами сверху и таб-баром внизу». Агент читает `CLAUDE.md`, где жёсткое
правило: брать готовые компоненты из `components/*.css` и значения из `tokens.css`,
никакого хардкода цветов, отступов и размеров шрифта; свой аналог кнопки верстать
запрещено, если в DS кнопка есть. Консистентность обеспечивается не аккуратностью
дизайнера и не ревью, а тем, что правило лежит в проекте и агент обязан ему следовать.

**Проверка — два независимых контура.** Перед коммитом `macket-rules-checker` сверяет
дифф с правилами и возвращает PASS/FAIL со списком нарушений в формате `файл:строка`
и подсказкой, как чинить (grep-first, только по диффу — дёшево). Если правка
интерактивная — навигация, таб-бар, анимация — подключается `screenshot-testing`: он
поднимает локальный сервер, открывает страницу в настоящем Chromium, имитирует тапы и
свайпы, снимает скриншоты, замеряет computed styles и присылает картинки. Это ловит
то, что чтением кода не поймаешь: что кнопка «назад» ведёт не туда, что таб-бар молча
заблокирован, что анимация идёт 1150 мс вместо заявленных 950.

**Онбординг.** Новый человек спрашивает `kirill`: «я новенький, с чего начать», «как
поменять контент», «почему не работает таб-бар». Агент отвечает конкретным файлом,
командой и скиллом. Живой наставник на это не тратится.

**Контент — отдельный контур.** Тексты, имена, аватарки, картинки лежат не в коде, а
в таблице. Скилл синхронизации читает листы, скачивает медиа в репозиторий, пережимает
в webp и запекает результат прямо в HTML между маркерами `FEED:START/END`. Два
следствия: контент правит **не дизайнер** (продакт или исследователь меняет текст в
таблице — прототип обновляется, дёргать умеющего в код не нужно), и прототип **не
зависит от сети и чужих CDN** — всё запечено в статику, открывается на телефоне в
переговорке без внешнего интернета. Синхронизация инкрементальная: сравнивается хэш
листа, неизменившееся не пересобирается; без правок прогон занимает секунды и не даёт
мусорного диффа.

**Публикация.** `git push` → CI собирает и выкладывает статику → готова ссылка.
Прототип полностью статический, бэкенда нет, поэтому «развернуть» = отдать файлы по
HTTP. У нас уже работают три пути: GitHub Pages, Yandex Object Storage, Docker. Для
внутреннего периметра нужен согласованный четвёртый — это в задачах фазы 1. Ссылку
можно кинуть в чат, открыть на созвоне или принести на юзабилити-тест. В этом и
разница с Figma: на выходе не картинка, а работающий продукт в руках у человека.

**Границы.** Это прототип, а не продакшен-код: его делают, чтобы проверить гипотезу, и
выбрасывают. Данные фиктивные, бэкенда нет, кроссбраузерность не гарантируется —
целимся в мобильный вебкит. Выращивать из него боевое приложение не надо, и продавать
его так тоже не надо.

### 1.3. Плагин против копии репозитория

| Критерий | Плагин | «Скопируйте наш репозиторий» |
|---|---|---|
| Обновления | Правило из одного БЮ приезжает во все | Копия расходится с первого дня |
| Что получает БЮ | Только метод | Метод + наши 47 чужих ему экранов |
| Версии | Видно, кто на чём сидит | Неуправляемо |
| Обмен опытом | Сетевой эффект | Ноль |

### 1.4. Путь дизайнера из другого БЮ

| Шаг | Что делает | Время |
|---|---|---|
| 1 | Репозиторий из шаблона → `/plugin install proto-kit` → `/proto-init` | 30 минут |
| 2 | Описывает экран словами — агент собирает из DS-компонентов, потому что правила это требуют | минуты |
| 3 | Линтер даёт PASS/FAIL, скриншот-агент прокликивает флоу и присылает картинки | автоматически |
| 4 | Продакт или исследователь правит контент в таблице, `/fetch-all` пересобирает страницы | секунды при инкрементальном прогоне |
| 5 | `git push` → автодеплой → ссылка в чат или на юзабилити-тест | минуты |

Ключевое: **дизайнер не пишет и не читает код.** За DS отвечают правила и линтер, за
работоспособность — скриншот-агент.

### 1.5. Критерии «сделано»

| Критерий | Проверка |
|---|---|
| Дизайнер незнакомого БЮ доходит от установки до задеплоенного экрана без помощи автора | За один рабочий день |
| Собранные им экраны проходят линтер | Без правок руками |
| Обновление плагина доезжает до всех и ничего не ломает | Релизный цикл |

## 2. Зачем и польза для больших БЮ

### 2.1. Что уже показал наш отдел

| Метрика | Значение |
|---|---|
| Кликабельных экранов | 47 HTML, ~34 000 строк разметки |
| DS-компонентов в работе | ~120 файлов `components/` |
| Срок | 9 июля → 2 августа, 51 коммит |
| Команда | отдел дизайна, **без выделенного фронтенд-разработчика** |
| Контент | 12 листов таблицы → статические данные, 133 МБ медиа в локальном кэше |
| Автоматика | 4 агента, 1 скилл, 11 скриптов синхронизации (~5 800 строк), git-хук |

Это не демо на коленке, а контур, переживший месяц ежедневной эксплуатации.

### 2.2. Что экономим и что улучшаем

| | Что | Почему это важно большому БЮ |
|---|---|---|
| **Экономим** | Время фронтенда на артефакт-выброс | Прототип — расходник: сделали, проверили гипотезу, выбросили. Отдавать на это инженера дорого, а без инженера дизайн упирается в статичную Figma |
| | Цикл «идея → проверяемый артефакт» | Вместо «поставить в спринт и ждать» — собрать самому за часы. При длинной очереди разработки это разница между «проверили до планирования» и «узнали после релиза» |
| | Онбординг | Агент-проводник отвечает на вопросы новичка вместо живого наставника. При текучке и подрядчиках — заметная статья |
| | Повторное набивание шишек | Каждое БЮ иначе пройдёт свой путь проб и ошибок и оплатит его отдельно. Тиражирование метода оплачивает его один раз |
| **Улучшаем** | Качество решений | Гипотеза проверяется на реальном контенте, в реальном браузере, на телефоне. Ошибки лейаута, тайминги, поведение на длинных текстах видны до разработки |
| | Консистентность DS | Правило «только DS-компоненты и токены» не висит в вики, а проверяется линтером перед коммитом. Там, где DS расползается быстрее всего, это самостоятельная ценность |
| | Готовность к исследованиям | На выходе не картинка, а кликабельная ссылка — можно нести на юзабилити-тест |

### 2.3. Главный аргумент и риск бездействия

| | |
|---|---|
| **Общая память вместо общего шаблона** | Находки копятся в git: инсайты по компонентам, память субагентов под версионным контролем. Раз в неделю куратор переносит устойчивые в чек-лист линтера. При общем плагине **грабли одного БЮ автоматически перестают быть граблями для всех** — форки этого не дают |
| **Если не делать** | Агенты в дизайне появятся у всех и так. Без общей упаковки — пять несовместимых огородов с разным качеством и безопасностью и нулевым обменом опытом. Сводить потом дороже, чем договориться сейчас |

## 4. Ресурсы, модели и инструменты

### 4.1. Люди

| Роль | Занятость | Зачем |
|---|---|---|
| Владелец инструмента | ~0.5 FTE постоянно | Упаковка, релизы, поддержка, разбор обратной связи. **Без явного владельца инициатива умирает на фазе 2** |
| Инженер (фронт/tooling) | на 4–6 недель фазы 1 | Разделение метода и контента, декларативный контент-контур, маркетплейс, деплой в периметре |
| Контакт от каждого пилотного БЮ | ~0.2 FTE на время пилота | Своя DS, свой контент, обратная связь |
| Технический писатель | разово, 1–2 недели | Документация в двух режимах |

### 4.2. Доступы и инфраструктура

| Что нужно | Статус |
|---|---|
| Лицензии Claude Code на команды пилотных БЮ | **Базовое условие** — без этого разговор не имеет смысла |
| Внутренний git-хостинг под маркетплейс и template-репозиторий | Нужно место и договорённость |
| Хостинг статики для прототипов | У нас описаны GitHub Pages, Yandex Object Storage, Docker; для внутреннего периметра нужен согласованный вариант |
| DS как подключаемый версионируемый артефакт | Договорённость с владельцами дизайн-системы |
| Источник контента (Google-таблицы или замена) | **Открытый вопрос**, снимается в фазе 0 |

### 4.3. Модели

| Модель | Где | Почему так |
|---|---|---|
| **Opus** | Сборка макетов, `screenshot-testing` | Визуальная проверка и сложные многошаговые сценарии |
| **Sonnet** | `macket-rules-checker`, `kirill` | Узкие задачи по чёткому чек-листу — дорогая модель не нужна |

Агенты работают grep-first и только по диффу — осознанное ограничение расхода,
прописанное в их инструкциях. Бюджет по токенам закладываем явно и меряем с пилота:
это единственная статья, растущая линейно от числа БЮ.

### 4.4. Инструменты

| Инструмент | Зачем | Требует закупки |
|---|---|---|
| Node.js 20+ | Скрипты синхронизации | Нет |
| Playwright + Chromium | Проверка в реальном браузере | Нет |
| `sharp` | Пережатие медиа в webp | Нет |
| git-хуки | Типографика на коммите | Нет |
| `@aws-sdk/client-s3` | Выкладка в объектное хранилище | Нет |

### 4.5. Риски

| Риск | Что делаем |
|---|---|
| У БЮ своя DS, метод не переносится «как есть» | Фаза 0 отвечает на это **до** вложений; линтер делаем DS-агностичным |
| Нет доступа к Google-таблицам в периметре | Абстрагировать источник контента, поддержать CSV/внутренние таблицы |
| Плагин поставили — не пользуются | Пилот привязан к реальной задаче с дедлайном, а не «попробовать» |
| Расползание версий и форки | Маркетплейс + версионирование + явный владелец |
| Расход токенов растёт с числом БЮ | Разделение моделей по задачам, grep-first, работа только по диффу; мерить с пилота |
