# Как расфорсить прототипирование с агентами на другие БЮ

Материал к выступлению. Отвечает на четыре заданных вопроса: образ результата,
зачем это нужно, список задач, необходимые ресурсы.

**Тезис в одну строку:** тиражировать нужно не прототип, а **обвязку вокруг него** —
правила сборки, агентов-проверяющих и контур данных. Упаковка — **плагин Claude Code
+ шаблон-репозиторий**, ставится в чужой БЮ за один день.

**Допущения** (не подтверждены, поправьте под факт):
целевой пользователь — дизайнер, который не пишет код; DS у БЮ в основном общая, но
фазу инвентаризации закладываем; цель выступления — получить добро и ресурсы на пилот
с 1–2 БЮ.

---

## 1. Образ результата

### 1.1. Что именно тиражируем

Сегодня в отделе дизайна работает связка из трёх слоёв. Ценность — в слоях B и C,
именно они и упаковываются.

| Слой | Что это | Тиражируется как |
|---|---|---|
| **A. Материал** | DS-компоненты (`components/`, ~120 файлов), токены (`tokens.css`), шрифты, иконки | Шаблон-репозиторий (GitHub template) или подключаемый пакет DS |
| **B. Метод** | Правила сборки (`CLAUDE.md`), спеки разделов (`docs/feeds-spec.md`), 4 агента, скилл `fetch-all`, git-хуки | **Плагин Claude Code** — главный артефакт |
| **C. Контент-контур** | Google-таблица как CMS → 11 fetch-скриптов → статический JSON + запечённый HTML + локальный медиа-кэш | Скилл + скрипты внутри плагина, шаблон таблицы отдельно |

### 1.2. Форма поставки: плагин, а не документ и не копия репозитория

Плагин Claude Code — это каталог, который кладёт в чужой проект сразу всё: скиллы,
субагентов, слэш-команды, хуки и настройки. Ставится двумя строками из внутреннего
маркетплейса:

```
/plugin marketplace add <внутренний-репозиторий-маркетплейса>
/plugin install proto-kit@ok-design
```

Почему именно плагин, а не «скопируйте наш репозиторий»:

- **Обновляемость.** Правило, выученное в одном БЮ, приезжает во все остальные
  обновлением плагина. Копия репозитория с первого дня начинает расходиться.
- **Не навязывает контент.** Плагин — это метод, а не 47 наших экранов. БЮ ставит его
  в свой проект со своими экранами.
- **Одна точка правды по версиям.** Видно, кто на какой версии метода сидит.

Строго говоря, поставка двойная: **плагин** (метод) + **template-репозиторий**
(пустой стартер с DS и настроенным деплоем), чтобы у БЮ без своего фронтенда была
точка старта, а не чистый лист.

### 1.3. Что внутри плагина

| Компонент | Тип | Что делает |
|---|---|---|
| `/proto-init` | команда | Бутстрап: спрашивает БЮ, DS, набор экранов; генерирует `CLAUDE.md` под этот БЮ, подключает деплой, заводит таблицу из шаблона |
| `fetch-all` | скилл | Синхронизация контента из таблицы: 12 листов, инкрементально по хэшу, медиа-кэш с пережатием в webp |
| `macket-rules-checker` | субагент | Линтер по правилам перед коммитом: DS-компоненты вместо самописных, токены вместо хардкода. Вердикт PASS/FAIL с `file:line` |
| `screenshot-testing` | субагент | Гоняет страницу в реальном Chromium: тапы, свайпы, скриншоты, замер computed styles. Проверяет, что интерактив реально работает |
| `kirill` | субагент | Проводник для новичка: «куда нажать, что сделать, как попросить». Заменяет человека-наставника на онбординге |
| `macket-insights-curator` | субагент по крону | Раз в неделю переносит устойчивые находки из инсайтов в чек-лист линтера и в правила |
| `pre-commit` | хук | Детерминированная типографика (неразрывные пробелы) на каждом коммите — без участия человека |

### 1.4. Как этим пользуется дизайнер из другого БЮ

Путь от нуля до кликабельного прототипа на своём контенте:

1. **День 0, 30 минут.** Создаёт репозиторий из шаблона, ставит плагин, запускает
   `/proto-init`. На выходе — работающий каркас со своей DS и настроенным деплоем.
2. **Дальше — словами.** «Собери экран ленты с карточками событий, табами сверху и
   таб-баром» → агент собирает из DS-компонентов, потому что правила это требуют.
3. **Проверка — автоматическая.** Перед коммитом линтер даёт PASS/FAIL, скриншот-агент
   прокликивает флоу в браузере и присылает картинки.
4. **Контент — в таблице.** Тексты, люди, картинки правит продакт или исследователь
   прямо в Google-таблице; `/fetch-all` пересобирает страницы (инкрементально —
   секунды, если правок нет).
5. **Публикация.** `git push` → автодеплой → ссылка, которую можно кинуть в чат,
   принести на юзабилити-тест или показать на демо.

Ключевое: **дизайнер не пишет код и не читает код**. Он описывает задачу и смотрит
результат; за соблюдение DS отвечают правила и линтер, за работоспособность —
скриншот-агент.

### 1.5. Что считаем «сделано»

- Дизайнер незнакомого БЮ без помощи автора доходит от `/plugin install` до
  задеплоенного кликабельного экрана **за один рабочий день**.
- Собранные им экраны проходят `macket-rules-checker` без правок руками.
- Обновление плагина доезжает до всех подключённых БЮ и ничего им не ломает.

## 2. Зачем этим заниматься и в чём польза для больших БЮ

### 2.1. Что уже показал наш отдел (факты из репозитория)

| Метрика | Значение |
|---|---|
| Кликабельных экранов | 47 HTML, ~34 000 строк разметки |
| DS-компонентов в работе | ~120 файлов `components/` |
| Срок | 9 июля → 2 августа, 51 коммит |
| Команда | отдел дизайна, без выделенного фронтенд-разработчика |
| Контент | 12 листов таблицы → статические данные, 133 МБ медиа в локальном кэше |
| Автоматика | 4 агента, 1 скилл, 11 скриптов синхронизации (~5 800 строк), git-хук |

Это не демо на коленке — это работающий продакшен-контур прототипирования, который
пережил месяц ежедневной эксплуатации.

### 2.2. Что экономим

- **Время фронтенда, потраченное на выброс.** Прототип — расходный материал: его
  делают, чтобы проверить гипотезу, и выбрасывают. Отдавать на это инженера дорого,
  а без инженера дизайн упирается в статичную Figma. Контур снимает эту развилку.
- **Цикл «идея → проверяемый артефакт».** Вместо «поставить в спринт фронтендеру и
  ждать» — собрать самому за часы. Для больших БЮ с длинной очередью разработки это
  разница между «проверили гипотезу до планирования» и «узнали после релиза».
- **Онбординг.** Агент-проводник (`kirill`) отвечает на вопросы новичка вместо
  живого наставника. У больших БЮ с текучкой и подрядчиками это заметная статья.
- **Повторное набивание шишек.** Каждое БЮ иначе всё равно пройдёт свой путь проб и
  ошибок с агентами — и оплатит его отдельно. Тиражирование метода оплачивает его
  один раз.

### 2.3. Что улучшаем

- **Качество решений.** Гипотеза проверяется на реальном контенте, в реальном
  браузере, на телефоне — а не на статичном макете. Ошибки лейаута, тайминги
  анимаций и поведение на длинных текстах видны до разработки, а не после.
- **Консистентность DS — принудительно.** Правило «только DS-компоненты и токены,
  никакого хардкода» не висит в вики, а проверяется линтером перед коммитом. Для
  больших БЮ, где DS расползается быстрее всего, это самостоятельная ценность.
- **Готовность к исследованиям.** На выходе — не картинка, а кликабельная ссылка,
  которую можно нести на юзабилити-тест.

### 2.4. Главный аргумент: общая память, а не общий шаблон

Находки в этом контуре не остаются в голове автора. Они копятся в git: инсайты по
компонентам, память субагентов (`.claude/agent-memory/` под версионным контролем),
а раз в неделю куратор переносит устойчивые из них в чек-лист линтера и в правила.

Если БЮ сидят на общем плагине, это даёт сетевой эффект: **грабли, найденные одним
БЮ, автоматически перестают быть граблями для всех остальных.** Пять форков этого
не дают. Именно поэтому тиражировать надо через плагин, а не рассылкой архива.

### 2.5. Риск бездействия

Агенты в дизайне появятся у всех и так. Без общей упаковки получим пять
несовместимых огородов с разным качеством, разной безопасностью и нулевым обменом
опытом — а сводить их потом дороже, чем договориться сейчас.

## 3. Первый подход к списку задач

Оценки — грубые, для разговора о ресурсах; уточняются после фазы 0.

### Фаза 0. Инвентаризация и пилот (2–3 недели)

Цель — проверить переносимость на живом БЮ до того, как что-либо строить.

1. Выбрать 1–2 пилотных БЮ и конкретную задачу прототипирования в каждом
   (не «попробовать инструмент», а реальную гипотезу с дедлайном).
2. Инвентаризация DS у пилотов: та же система или своя, есть ли токены, в каком виде
   доступны компоненты. **Это главная развилка проекта** — от неё зависит, будет ли
   DS частью плагина или подключаемым адаптером.
3. Инвентаризация контент-контура: доступна ли Google-таблица в их периметре, нужна
   ли замена (внутренние таблицы / CSV / БД).
4. Ручной перенос «как есть» на пилотном БЮ силами нашего отдела — с фиксацией
   каждого места, где пришлось править под чужой контекст. Этот список правок и есть
   ТЗ на фазу 1.
5. Замерить точку отсчёта: сколько времени у них сейчас занимает кликабельный
   прототип и чьими силами.

### Фаза 1. Упаковка (4–6 недель)

6. Разделить репозиторий на «метод» и «контент»: вынести из `CLAUDE.md` и агентов всё
   специфичное для нашего продукта (названия лент, гейты онбординга, наши экраны).
7. Собрать плагин `proto-kit`: манифест, скиллы, агенты, хуки, команды.
8. Написать команду-бутстрап `/proto-init` — интерактивная настройка под БЮ вместо
   ручного редактирования конфигов.
9. Сделать правила и линтер **DS-агностичными**: правило «бери из DS» должно читать
   реестр компонентов и токенов проекта, а не знать наш наизусть.
10. Развернуть внутренний маркетплейс плагинов (репозиторий с манифестом) и процесс
    выпуска версий.
11. Сделать template-репозиторий: пустой стартер с подключённой DS, настроенным
    деплоем и хуками.
12. Обобщить контент-контур: `fetch-*`-скрипты сейчас знают наши листы. Нужен
    декларативный конфиг «лист → схема → шаблон» и шаблон таблицы для нового БЮ.
13. Развязать деплой: сейчас поддержаны GitHub Pages, Object Storage, Docker. Описать
    и проверить путь для внутреннего периметра.
14. Документация в двух режимах: «за 30 минут до первого экрана» и «полный справочник».

### Фаза 2. Раскатка (параллельно, от 2 недель на БЮ)

15. Установка у пилотных БЮ по написанной инструкции — **без нашего участия**, мы
    только наблюдаем и записываем, где споткнулись.
16. Воркшоп на 2 часа: как формулировать задачу агенту, как читать вердикт линтера.
17. Собрать обратную связь, поправить бутстрап и документацию по её итогам.
18. Витрина: страница со ссылками на прототипы всех БЮ — работает и как инструмент
    обмена, и как доказательство пользы.

### Фаза 3. Сопровождение (постоянно)

19. Регламент обновлений плагина и версионирование.
20. Куратор инсайтов по крону — уже работает у нас, распространить на общий чек-лист.
21. Канал поддержки и разбор кейсов.
22. Метрики: число БЮ на плагине, число собранных прототипов, время «идея → ссылка»,
    доля прогонов линтера с PASS с первого раза.

## 4. Необходимые ресурсы, модели и инструменты

### 4.1. Люди

| Роль | Занятость | Зачем |
|---|---|---|
| Владелец инструмента | ~0.5 FTE постоянно | Упаковка, релизы, поддержка, разбор обратной связи. Без явного владельца инициатива умирает на фазе 2 |
| Инженер (фронт/tooling) | на 4–6 недель фазы 1 | Разделение метода и контента, декларативный контент-контур, маркетплейс, деплой в периметре |
| Контакт от каждого пилотного БЮ | ~0.2 FTE на время пилота | Своя DS, свой контент, обратная связь |
| Технический писатель | разово, 1–2 недели | Документация в двух режимах |

### 4.2. Доступы и инфраструктура

- **Лицензии Claude Code** на команды пилотных БЮ — базовое условие, без этого
  разговор не имеет смысла.
- **Внутренний git-хостинг** под маркетплейс плагина и template-репозиторий.
- **Хостинг статики** для прототипов: у нас уже описаны GitHub Pages, Yandex Object
  Storage и Docker. Для БЮ во внутреннем периметре нужен согласованный вариант.
- **DS как подключаемый артефакт** — договорённость с владельцами дизайн-системы
  о версионированной поставке компонентов и токенов.
- **Источник контента** — доступность Google-таблиц в периметре БЮ либо согласованная
  замена. Открытый вопрос, снимается в фазе 0.

### 4.3. Модели

Разделение по стоимости уже проверено у нас и переносится как есть:

- **Opus** — сборка макетов и `screenshot-testing` (визуальная проверка, сложные
  многошаговые сценарии).
- **Sonnet** — `macket-rules-checker` и `kirill`: узкие задачи по чёткому чек-листу,
  дорогая модель не нужна.
- Агенты работают grep-first и только по диффу — это осознанное ограничение расхода,
  прописанное в их инструкциях.

Бюджет по токенам стоит закладывать явно и мерить с пилота: это единственная статья,
которая растёт линейно от числа БЮ.

### 4.4. Инструменты в окружении

Всё уже используется, новых закупок не требует: Node.js 20+, Playwright + Chromium
(проверка в реальном браузере), `sharp` (пережатие медиа в webp), git-хуки,
`@aws-sdk/client-s3` для выкладки в объектное хранилище.

### 4.5. Риски

| Риск | Что делаем |
|---|---|
| У БЮ своя DS, метод не переносится «как есть» | Фаза 0 отвечает на это до вложений; линтер делаем DS-агностичным |
| Нет доступа к Google-таблицам в периметре | Абстрагировать источник контента; поддержать CSV/внутренние таблицы |
| Плагин поставили — не пользуются | Пилот привязан к реальной задаче с дедлайном, а не «попробовать» |
| Расползание версий и форки | Маркетплейс + версионирование + явный владелец |
| Расход токенов растёт с числом БЮ | Разделение моделей по задачам, grep-first, работа только по диффу; мерить с пилота |

## Одностраничная выжимка для слайда

- **Что:** плагин Claude Code `proto-kit` + template-репозиторий. Тиражируем метод, а
  не макеты.
- **Как пользоваться:** две команды на установку, `/proto-init` на настройку, дальше
  дизайнер описывает экран словами; агенты проверяют DS и прокликивают в браузере;
  контент правится в таблице; push — и готова ссылка.
- **Зачем:** отдел дизайна без фронтенд-разработчика собрал 47 кликабельных экранов
  за 3.5 недели. Экономим время инженеров на выброс и цикл проверки гипотез, улучшаем
  консистентность DS принудительно, а не на честном слове.
- **Почему общий плагин:** грабли, найденные одним БЮ, перестают быть граблями для
  всех. Форки этого не дают.
- **Просьба:** 1–2 пилотных БЮ, инженер на 4–6 недель, владелец на 0.5 FTE, лицензии
  и место под внутренний маркетплейс.
